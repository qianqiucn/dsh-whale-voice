# Whale Voice · ChatGPT 工程任务书详细程度标准

> **适用对象：** ChatGPT 编写和审核交给 DeepSeek 的开发计划书。**不把本文件中的计划管理义务强加给 DeepSeek。**
>
> **最高规则：** 用户要求“计划书尽可能详细，留给 DS 思考的空间越少越好，它只需要执行”。因此任务书应当是**决策充分、可逐项实施、可客观验收、可回滚和安全边界明确的工程规格**，而不是开放式 brainstorming。
>
> **记忆入口：** [CHATGPT_LONG_TERM_MEMORY.md](CHATGPT_LONG_TERM_MEMORY.md)。**完整填写模板：** [TASK_SPEC_TEMPLATE.md](TASK_SPEC_TEMPLATE.md)。

## A. 派发前的“决策完成”门槛（全部必过）

ChatGPT 在 GitHub 中更新/发送每一份新的**可执行**任务书前，应检查：

- [ ] **实际现状**：核验最新 main、当前功能 PR HEAD、已有实现、CI、阶段等级。标识哪些事实来自源码/CI，哪些来自用户报告，哪些仅是设计候选。
- [ ] **没有重复任务**：目标文件/接口/测试是否已存在？已实现内容必须改为“检查与验收”，而非让 DeepSeek 重新实现。
- [ ] **明确单一结果**：能用一两句说清任务交付物和本阶段不会完成的事项；不混合多个高风险生产阶段。
- [ ] **路径清晰**：指出精确的仓库相对路径、建议新增文件名、关键函数/导出和调用方。如果代码实际不符，先只读核对并按明确分支规则处理，不让 DS 猜路径。
- [ ] **接口完备**：需要的输入/输出形状、Schema version、必填/可选/未知字段、状态机、error code、超时/取消/重试/并发/幂等和安全边界明确；文档审计任务则列出具体待查证问题与记录格式。
- [ ] **选择明确**：从多个方案中给出一个推荐方案及否决原因；真不确定时限定可核实条件 A/B 和对应动作，不能只写“自行选择最合适方式”。
- [ ] **步骤可逐项完成**：编号顺序包含准备、最小代码改动、隔离/负向测试、文档、Git、CI、验收停止条件。
- [ ] **已有功能保护**：特别明确 WeChatAgent、Whale Voice/Relay、Bridge/Worker、安全闸门、UNKNOWN、不真实发送、Config SAVED/APPLIED 等不可破坏约束。
- [ ] **测试具可判定预期**：对每个核心行为给出至少一个成功和一个拒绝/异常例；写出命令与预期 PASS/失败行为，不只写“测试一下”。
- [ ] **用户权限清楚**：列出默认获准的低风险动作与严格需要单独授权的高风险动作；绝不以“任务书已发”推导生产操作许可。
- [ ] **完成定义清楚**：PR 范围、报告字段、测试、CI、验收等级与哪些条件可打 DONE；合并不自动发生。
- [ ] **完成自审**：用下一节的质量评分打分，有一项阻塞则不发送给 DeepSeek 执行。

## B. 标准任务书必须具备的 16 节

推荐按以下顺序，详见模板：

1. **任务 ID、唯一标题、目标、阶段状态**：明确任务是否设计/OFFLINE/真实集成。
2. **为什么做 & 精确的业务结果**：用户需求、产品边界，明确“完成后会看到/能调用什么”。
3. **最新事实与证据**：main/PR/HEAD/CI 的检查日期；当前源码能力、既有功能；已知未知，不能用旧快照充数。
4. **依赖与入口**：哪份计划/PR 必须先完成、哪几个源文件/文档必须先读。
5. **本次范围与非目标**：in-scope/out-of-scope 文件、后续阶段边界，禁止偷跑。
6. **技术方案与责任分工**：明确层次与数据流，避免把业务 Core/Relay/WeChatAgent 角色混用。
7. **要改/新建的文件清单**：每文件目的、拟加/改函数或导出、为何改、明确禁止修改的文件。
8. **数据与接口契约**：精确形状/类型/Schema/状态与错误语义；必要时给示例 fixture，但不是未经验证的虚构生产 API。
9. **执行步骤**：按“先核验 → 实施 1 → 实施 2 → 负向检查 → 构建/CI → 报告”编号；每步可判断成功。
10. **异常处理决策树**：版本不符、API 缺失、网络超时、回滚未知、并发冲突等各自固定处理策略。
11. **安全、隐私、权限**：写明绝对不能做的动作，及如何失败关闭；敏感数据不写入 PR。
12. **迁移与兼容**：旧配置/历史数据/版本变化的处理及回退路线；明确无迁移时“无须迁移”。
13. **测试矩阵**：成功/失败/边界/权限/隔离/负载或 UI 的输入—预期—证据，使用已有工具。
14. **Git / PR 纪律**：分支基点、复用现有 PR 还是创建新的、变更范围、CI、是否允许合并（默认不允许）。
15. **验收标准（DoD）**：逐条可检查、量化、标记应维持的等级；何时视为完成。
16. **交付报告模板与停止条件**：文件/函数、测试计数、PR/Commit、剩余风险、禁止超范围继续。

**不是要求每次都写极长的理论说明，而是要求每一项实际会影响实现的决策都明确。** 纯文档任务可以将“不涉及”标为 N/A 并说明原因，不能凭空虚构接口来填模板。

## C. 清晰度与可执行性（禁止的写法）

下面这些措辞**单独出现时不合格**：

| 模糊措辞 | 应改写成 |
|---|---|
| “自行选择一个适合的实现” | “采用方案 A，优先原因 X；若官方接口不存在则只做只读审计并返回 `BLOCKED_API_MISSING`” |
| “做好错误处理” | “覆盖超时/403/409/无效 JSON/空音频；分别返回明确状态，不重试可能已提交的发送” |
| “支持多个模型” | “注册表按 Provider ID 返回候选，明确不得将 `NOT_IMPLEMENTED` 渲染为可选” |
| “参考原有代码” | “先读取路径 A/B 中指定模块和相应测试，复用现有导出；发现不一致时只记录差异和停机条件” |
| “实现 UI 并测试” | “列出页面、可交互与禁用控件、Mock/真实标签、Playwright 选择器和窄窗口验收” |
| “修复所有问题” | “只处理本轮列出的错误码/文件/状态，其他风险写报告，不扩大改动范围” |
| “合理设置超时或重试” | “以现有契约中的 timeoutMs/retry policy 为准；外部副作用 UNKNOWN 禁止重试，未定义值则不静默设置” |
| “让用户体验更好” | “给定页面名称、状态文案、不可用原因及切换时行为，验收按元素查询” |

额外禁忌：
- 不要用“差不多”“一般来说”“应该可以”当成技术事实或测试证据。
- 不要把精确的假 API、硬编码私人本机路径、臆造模型版本和未经核验的返回值写成实现要求。
- 不要要求 DeepSeek 自己重新定义核心范围、编排计划优先级、判定产品默认 Provider 或承担 ChatGPT 的 DONE 打标。
- 不要把离线 Fake 契约成功说成真实模型/微信已经连接。

## D. 不可核实信息的固定处理方式

当必需事实不确定：

1. **优先读已安装/仓库源码及可信上游文档**，明确来源与版本。
2. 可读、可核实：采用事实驱动的唯一推荐实现路径。
3. API 不存在或版本不匹配：**不要猜接口；改做隔离能力判断**，把真实功能标 `UNSUPPORTED` / `VERSION_UNKNOWN` 等，并回报证据。
4. 两个方案都合理：ChatGPT 应在计划派发前做选择并写出取舍，不把方案列表交给 DeepSeek 随意决定。
5. 会触及生产/敏感资产/微信发送/未知 DLL/收费 API：**立即停止该类操作，等待单项授权**。已安全的文档/测试仍可独立完成。
6. 如果代码已经提前实现某条计划：对照验收矩阵做核对；**不要为了“执行步骤”重复改写已通过的代码**。

## E. 计划详细程度分级

- **Level 0 · IDEA**：仅用户创意；不许直接交给 DeepSeek 实现。
- **Level 1 · ROADMAP**：有范围和依赖，但无精确接口/测试；只能留在计划总表。
- **Level 2 · EXECUTION-READY（默认派发门槛）**：16 节完整或 N/A 有理由、无重大未决产品决策、文件/接口/异常/测试/DoD 具体；**可发送**。
- **Level 3 · PRODUCTION-CHANGE-READY**：Level 2 加入具体安全审查、回滚演练、真实组件/账号风险以及**该次生产变更的用户单独授权**。没有授权永远不能由任务文案直接升级。

**重要：目前仓库里部分 01–14 是路线条目，不自动视作 EXECUTION-READY。每次用户要下一份时，ChatGPT 必须先扩写为 Level 2，再发送与写入 GitHub。**

## F. ChatGPT 派发前自审评分（100 分）

评分仅作为自查，不是模型性能评估：

| 项 | 分值 |
|---|---:|
| 真实基线/避免重复 | 15 |
| 单一目标与范围边界 | 10 |
| 模块与文件级操作具体 | 15 |
| API/状态/失败/迁移契约 | 15 |
| 有序步骤与决策树 | 15 |
| 正负面测试与验收 | 15 |
| 安全、权限、隐私与回滚 | 10 |
| 完成报告、PR/CI 与停止条件 | 5 |

**低于 90 分不能作为工程实现计划发送。** 任何强制门禁失败（虚构接口、生产行为未授权、与现有安全协议冲突、实际代码未核实却宣称确定）都一票否决，无论总分多少。

报告/研究计划若没有代码修改，其文件级/协议项可以依据具体审计路径、证据记录格式和安全查询规则获得满分；不能为了填模板而乱加生产接口。

## G. 任务完成验收与 Git 标记

- 只有检查全部 DoD，并能对照 PR 最新 HEAD、CI、测试或明确的只读证据，才标 `DONE`。
- 分别跟踪 Git `PR_OPEN`/`MERGED` 与功能 `OFFLINE`/`INTEGRATED`/`VERIFIED`。
- 发送后发现范围有变，更新该计划书版本、依赖、变更原因和变更日志；**明确告诉用户已发送版本发生了什么变化**，避免 DeepSeek 两套任务同时执行。
- 只有 ChatGPT 负责更新本仓库的计划管理文件。DeepSeek 仍可进行被授权的功能代码开发与工程 PR，而不需要额外计划管理操作。
